01 — The Gap

Existing guardrails validate the action. Nobody validates the story.

Agent guardrails today — amount ceilings, scope, PII handling, audit logging — all check the refund against the merchant's configuration. When the requested amount sits inside the limit and the underlying fact is false, every one of those guardrails passes it, because none of them ever looks at the payments ledger. Four major Indian PSPs have publicly written about this exact scam and shipped no detector for it — their own advice is "verify the UTR against your bank statement," which is precisely the check nothing in the stack automates.

Customer claim → nothing checks it against reality → Agent decides → Config guardrails → Money moves

Ledger Oracle sits in the hole in that diagram. It doesn't replace config guardrails or fraud-scoring vendors that watch for serial abusers — it answers a narrower, upstream question those systems never ask: is this specific claim, about this specific order, actually reflected in the ledger?

02 — How It Decides

The agent investigates. It never decides.

Every claim goes through two halves with a hard wall between them. The first half is a bounded LLM agent that gathers evidence by calling read-only tools against the payments ledger. The second half is a plain deterministic function that looks at that evidence and returns a verdict. The model is never in the room when the decision gets made — structurally, not by convention.

Step 1 — Bounded Investigation Agent
agent.py
Max 5 tool calls, max 2 retries per tool, 30s wall-clock budget — then it stops and escalates instead of hanging. It can only call the five tools below; it has no field, anywhere in its output types, that can express a decision.

Step 2 — Deterministic Policy Engine
policy.py — decide()
Takes the evidence the agent collected and returns a verdict by plain comparison against the ledger — no LLM call, no network call, no randomness, in this function or anywhere it imports from. Its own docstring states the contract in four words: "DECIDES. No network. No model. No randomness."
Pass
Claim matches ledger evidence within tolerance.
Block
Claim contradicts what the ledger shows.
Escalate
Evidence is insufficient or in-flight — a human decides, not a guess.

03 — On Money

The system that investigates refunds cannot move a rupee.

All five tools are read-only. There is no write path.

Every tool the agent can call is registered with mutates=False, and the connection they run against opens the ledger in mode=ro — a mutation isn't blocked by convention, it raises a SQLite error. There's no issue_refund tool in the agent's allowlist at all; it was left out on purpose. This isn't a limitation of the demo — it's the safety argument.

  • The agent gathers evidence. It cannot act on it.
  • The verdict carries max_refundable_paise — a bounded ceiling the engine authorizes for a human reviewer or a downstream payout system to act on, not a disbursement. Nothing on this page, or in this system, ever credits money.
  • Escalate routes to a human queue — /review — and only an explicit human approve ever marks a claim's reference as consumed, closing the loop against replay.
